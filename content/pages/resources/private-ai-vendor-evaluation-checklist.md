Private AI Vendor Evaluation: Evidence to Request
Healthcare systems, multi-location operators, and regulated service firms routinely receive vendor decks that label shared cloud software as private AI. Treating that phrase as an architectural fact exposes patient inquiries, proprietary acquisition data, and internal workflows to undisclosed sub-processors and contract lock-in. This evaluation framework details the inspectable technical, operational, and contractual evidence procurement teams should collect before signing an agreement.

Private infrastructure vs. shared API wrappers
In vendor demonstrations, four distinct technical architectures are frequently sold under the same "private AI" label. A buyer evaluating marketing automation, call intelligence, clinical intake triage, or internal knowledge tools cannot assess risk or long-term economics until the vendor proves which deployment tier powers the product. Sales language blurs the boundary between a custom interface sitting on top of a public commercial model and isolated compute dedicated to one organization.
Procurement teams should start every evaluation by placing the vendor's proposed system into a four-row architectural comparison. Mapping the deployment model early prevents misplaced security reviews and clarifies which operational trade-offs the buyer is accepting.
* Shared SaaS Wrapper; Where Inference Runs: Multi-tenant public cloud infrastructure owned by third-party model providers; Network and Data Boundary: Prompts travel over standard internet APIs through the vendor's shared application server; Sub-Processor Exposure: High: vendor platform, external model provider, logging tools, and analytics layers all process inputs; Control and Commercial Trade-Off: Lowest upfront setup effort, minimal isolation, weak auditability, and high exposure to upstream policy changes
* Enterprise Commercial API (Zero-Retention); Where Inference Runs: Vendor-managed commercial cloud endpoints under an enterprise data-processing addendum; Network and Data Boundary: Encrypted transit to commercial endpoints with contractual opt-out from shared model training; Sub-Processor Exposure: Moderate: commercial model provider remains in the data path alongside the application vendor; Control and Commercial Trade-Off: Strong frontier model capability, while buyers remain dependent on external uptime, rate limits, and third-party terms
* Dedicated Single-Tenant Cloud (VPC); Where Inference Runs: Isolated virtual private cloud or reserved cloud GPU instances dedicated to one customer account; Network and Data Boundary: Private network peering, customer-controlled firewalls, and isolated storage volumes; Sub-Processor Exposure: Low to moderate: cloud hyperscaler hosts the infrastructure while external model calls can be restricted; Control and Commercial Trade-Off: High scalability and strong network segregation, offset by ongoing cloud compute spend and configuration overhead
* Owned Local Inference Infrastructure; Where Inference Runs: Dedicated physical hardware operated within an organization's or partner's controlled environment; Network and Data Boundary: Data remains inside defined local network boundaries with explicit rules governing any external egress; Sub-Processor Exposure: Minimal for local workloads: open-weight models execute without external model API calls; Control and Commercial Trade-Off: Maximum operational control, predictable utilization, and strict data sovereignty, requiring hardware capital and internal engineering stewardship
Not every marketing or business workload requires offline local inference. Running top-of-funnel keyword research or drafting public website outlines carries a very different risk profile than analyzing recorded patient intake calls, structuring CRM conversion cohorts, or summarizing privileged professional services records. Using commercial APIs is often practical when data classification permits it, whereas paying a premium for "private AI" while unknowingly deploying a shared wrapper on sensitive first-party data creates avoidable exposure.
To establish this architectural baseline before advancing a vendor to security review, request three foundational artifacts:
* A signed system architecture diagram identifying every compute node, model endpoint, vector database, and application server involved in processing a single user request from ingress to response.
* A model provenance list specifying the exact commercial APIs or open-weight models invoked by each feature, including fallback models triggered during traffic spikes or outages.
* A multi-tenancy disclosure explaining whether customer data is separated logically (by database row or tenant ID inside shared infrastructure) or physically (by isolated compute nodes, dedicated storage volumes, and separate network segments).
If a vendor refuses to disclose whether a workflow calls external commercial endpoints or relies on shared multi-tenant vector indexes, procurement should classify the tool as a shared SaaS wrapper regardless of how the pitch deck describes it.
Compute hosting, network isolation, and data residency
Once a vendor confirms its deployment tier, IT and security reviewers need verifiable evidence of where data physically lives and how network traffic is constrained. High-level assurances that data stays "in the cloud" or "in a private environment" fail basic enterprise scrutiny because modern AI applications chain together multiple microservices, search indexes, and background queues. Data entering through a secure web portal can spill into an unsegmented logging cluster or an offshore backup region when network boundaries are loosely configured.
### Topology diagrams and physical compute verification
Ask the vendor to walk your infrastructure lead through a live network topology diagram rather than a simplified marketing schematic. The diagram should trace ingress points, load balancers, private subnets, inference servers, embedding databases, and outbound gateways. Pay close attention to three boundary questions:
* Compute isolation at the runtime layer: On GPU-backed inference nodes, confirm whether memory buffers and model caches are dedicated to a single tenant or shared across multiple customers running concurrent workloads.
* Egress filtering and outbound locks: If the deployment is marketed as isolated or locally hosted, verify whether firewall rules block arbitrary outbound internet calls from inference containers. An isolated server with unrestricted outbound access can still transmit telemetry, crash dumps, or prompt payloads to external services.
* Geographic residency for primary and secondary storage: Confirm the physical jurisdictions for active inference and primary databases as well as disaster-recovery replicas, automated snapshots, and staging environments used for software testing.
### Encryption boundaries and hardware ownership
Standard transport encryption and default cloud storage encryption establish a baseline, yet neither proves private AI rigor. When evaluating sensitive healthcare, multi-location, or professional services deployments, examine how encryption keys are generated, stored, rotated, and revoked. For dedicated cloud deployments, request documentation showing whether the buyer can supply customer-managed encryption keys (CMEK) so the vendor cannot decrypt stored archives independently after a relationship ends.
Buyers working with agencies or technology partners that operate owned physical servers should also keep one legal and operational distinction clear: hardware ownership is completely separate from data ownership. Operating owned, local AI infrastructure allows an operator to control inference boundaries, software configurations, and utilization economics, yet owning the compute hardware never transfers ownership of client data. Every agreement involving partner-hosted or vendor-owned local infrastructure must state in plain language that the buyer retains sole legal title to all raw inputs, derived embeddings, structured outputs, and performance records stored on those machines.
Before clearing the infrastructure gate, collect these five records:
* Network boundary and egress specification showing allowed ports, private endpoints, and blocked external routes.
* Hosting and region schedule naming the data-center provider or physical facility tier, primary hosting region, and backup locations.
* Encryption and key-management policy detailing algorithms in transit and at rest, key rotation intervals, and key-custody roles.
* Vulnerability management and patching cadence explaining how operating systems, container images, and model-serving frameworks are updated without exposing customer payloads.
* Environment separation proof confirming that production customer data is never copied into shared developer sandboxes or sales demonstration instances.
Data retention, training exclusions, and sub-processor chains
Even when primary compute looks tightly isolated, privacy failures frequently occur in the secondary plumbing that surrounds an AI application. Vendors routinely point to a zero-retention clause from an upstream model provider while overlooking other layers inside their own stack that store raw text, audio transcripts, or user identifiers for weeks or months.
### Inspecting retention windows across every layer
A credible private AI vendor should produce a layer-by-layer data lifecycle table specifying exact retention durations and deletion mechanisms for every artifact generated during normal operations. Evaluate each of the following storage tiers individually:
* Raw prompts and uploaded documents: How long do user inputs, uploaded PDFs, intake call transcripts, or CRM exports persist in application memory, temporary disk storage, or message queues after a response is returned?
* Model outputs and conversation histories: Are generated answers stored indefinitely to power user chat histories, and can administrators configure automated time-to-live (TTL) purge schedules by department or workflow?
* Vector embeddings and retrieval indexes: Retrieval-augmented generation (RAG) systems convert proprietary documents into numerical vectors stored inside search indexes. Because embeddings can retain sensitive semantic information and are often paired with raw text chunks for citation display, verify how quickly deleting a source document removes its associated chunks and vectors from every replica.
* Observability, error logs, and evaluation queues: Engineering teams routinely capture full request and response payloads inside observability platforms to debug slow queries or inaccurate responses. Demand proof that prompt bodies and sensitive fields are scrubbed before logs leave the isolated environment.
* Automated backups and snapshots: Zero-retention in a live database means very little if encrypted daily snapshots retain deleted records across extended backup cycles without a documented expiration schedule.
### Training exclusions and derivative data rights
Contractual language around model training requires line-by-line review by legal and operations stakeholders. Require an explicit prohibition barring the vendor, its affiliates, and its downstream model providers from using buyer prompts, completions, uploaded files, call recordings, attribution datasets, or human feedback ratings to train, fine-tune, or evaluate any model shared with other customers.
Watch closely for broad carve-outs permitting the vendor to retain "aggregated," "anonymized," or "de-identified" service data to improve its products. In specialized markets such as multi-location healthcare or competitive regional services, aggregated prompt patterns, conversion benchmarks, and intake-objection language can represent valuable commercial intelligence. If a vendor wants to collect operational telemetry such as system latency, token volume, or uptime counts, the contract should restrict collection strictly to technical performance metrics stripped of business content, patient attributes, and customer identifiers.
### Mapping the complete sub-processor chain
Most modern AI platforms orchestrate multiple specialized tools behind a single login. A single workflow might pass an audio recording to a transcription vendor, run optical character recognition (OCR) on an attached form via a second provider, query a managed vector database hosted by a third party, and send alerts through an email relay operated by a fourth company.
Require a complete, dated sub-processor register covering every third party that processes, stores, or transmits customer data. For each sub-processor, the register should state the entity's legal name, geographic processing location, exact functional role, and data categories accessed. The contract should also grant advance written notice before any new sub-processor is onboarded and provide a practical right to object or terminate without penalty if a newly added provider violates the buyer's risk threshold.
Access controls, audit trails, and human governance
Architecture diagrams and contractual promises hold up only when daily operational discipline enforces them. Picture a procurement evaluator and an IT security reviewer standing side by side at a workstation during a pre-signature technical walkthrough, examining a live staging console with the vendor's solutions architect. Instead of watching another rehearsed prompt demonstration, the evaluator opens the administrative permissions panel, tests whether a standard marketing coordinator can view clinical intake logs, requests an export of recent query audit records, and asks the engineer to show what vendor support personnel see when a customer submits a troubleshooting ticket.
That brief live inspection routinely uncovers gaps that lengthy security questionnaires conceal. Private AI governance depends on an inspectable chain of identity controls, immutable activity records, and human review gates.
### Role-based access and support-staff boundaries
Enterprise buyers managing multiple departments, clinics, or regional offices need granular access separation. A marketing manager optimizing landing-page copy should not inherit query access to HR records, legal briefs, or protected clinical intake transcripts simply because both teams share the same AI platform.
Request live verification and written documentation for these access controls:
* Enterprise identity integration: Support for single sign-on (SSO) via SAML or OpenID Connect, enforced multi-factor authentication (MFA), and automated user deprovisioning via SCIM so departing employees lose access immediately.
* Role-based and attribute-based permissions: Ability to restrict specific models, knowledge repositories, and prompt histories by role, business unit, or physical facility location.
* Vendor engineer access restrictions: Proof that vendor support and engineering staff hold zero standing access to production customer prompts or knowledge bases. Any troubleshooting access must require customer-initiated approval, scoped permissions, time-bound expiration, and full session logging.
### Prompt logging, output review, and escalation paths
When an AI system drafts patient education copy, summarizes intake calls, or triggers CRM routing actions, leadership needs an auditable record of how every output was produced. Weak audit trails make incident response, quality assurance, and regulatory inquiries hard to resolve cleanly.
Demand inspectable audit-log schemas demonstrating that the platform captures four core elements:
* Actor and timestamp identity: Which authenticated user or automated service account initiated the request, from which IP range or workspace, and at what exact UTC timestamp.
* Model and configuration version: Which model identifier, system prompt version, and temperature or safety settings executed the task.
* Retrieved context references: Which internal knowledge documents or database records were pulled into the prompt context to generate the response.
* Human approval and downstream action: Whether a designated human reviewer edited, approved, or rejected the output before it was published externally, emailed to a prospect, or written into a system of record.
Human governance matters as much as software logging. In healthcare, financial services, and legal environments, autonomous publishing without structured human review invites factual errors, unauthorized clinical claims, and brand drift. Ask the vendor how its platform enforces approval workflows, separates draft staging from live publication, and documents change owners when system prompts or retrieval rules are updated.
Regulated-industry boundaries and HIPAA-aware realities
Regulated buyers face a persistent marketing myth: that deploying a private model or running inference on local servers automatically solves regulatory compliance. Vendors sometimes reinforce this misconception by placing compliance badges near AI feature descriptions without clarifying the legal scope of those claims. Procurement teams in hospitals, health systems, behavioral health networks, and regulated professional services must separate technical privacy boundaries from statutory compliance obligations.
### Separating HIPAA-aware architecture from compliance claims
No AI model, cloud instance, or local server makes an organization HIPAA-compliant on its own. Regulatory compliance across healthcare depends on administrative, physical, and technical safeguards spanning the covered entity, its workforce training, its internal policies, its incident-response readiness, and the contractual obligations of every business associate touching protected health information (PHI). Software infrastructure can be designed to be HIPAA-aware, supporting strict access controls, audit logging, encryption, data minimization, and isolated processing, without claiming a blanket legal certification that software alone cannot provide.
When evaluating any AI vendor that may encounter PHI or sensitive patient inquiry details, request concrete contractual and operational proof rather than marketing assurances:
* Scope-specific Business Associate Agreement (BAA): Confirm whether the vendor will execute a BAA that explicitly covers the exact AI features, transcription tools, vector stores, and support workflows you are buying. Some established software vendors sign BAAs for their legacy core platform while carving out newer AI add-ons in the fine print.
* Downstream BAA chain verification: Confirm that every sub-processor handling PHI in the vendor's AI pipeline has also executed an upstream BAA with the vendor, or prove technically that PHI is stripped or processed strictly on local infrastructure where no third-party sub-processor receives it.
* Minimum-necessary data design: Evaluate whether the workflow actually needs identifiable patient records at all. Often, separating intake attribution from clinical documentation allows marketing and operations teams to measure performance accurately while keeping identifiable clinical content out of commercial marketing tools altogether.
* Breach notification timelines and incident cooperation: Review contractual timelines for notifying the buyer of unauthorized access, misrouted prompts, or sub-processor security events, along with forensic log availability during an investigation.
### Advertising platform constraints and sensitive vertical realities
Data sovereignty does not stop at the edge of an AI server. For hospitals, treatment centers, and multi-location healthcare groups, one of the highest-risk failure points sits at the handoff between internal intake systems, AI analytics tools, and paid advertising platforms.
Marketing Powered operates owned, local AI infrastructure for HIPAA-aware inference and works in LegitScript-aware and HIPAA-aware environments built for Google's sensitive healthcare vertical, where retargeting is not permitted, while tracking attribution to admission rather than stopping at lead counts. That operational reality highlights a direct evaluation question for any healthcare buyer: how does the AI vendor prevent sensitive health indicators, diagnostic terms, or caller identities from leaking into third-party ad pixels, browser cookies, or unauthorized audience-matching uploads?
Ask prospective vendors to document how their system handles three intersection points:
* Call tracking and transcription boundaries: If AI summarizes inbound patient calls to classify inquiry intent or measure intake team responsiveness, verify where audio files are stored, whether sensitive health disclosures are redacted before CRM syncing, and whether any transcript fields are ever pushed to external ad networks.
* Conversion event payloads: When passing offline conversion signals (such as verified appointments or admissions) back to paid media platforms to improve conversion value per cost, confirm that only permitted, non-sensitive conversion identifiers are transmitted and that strict server-side filtering blocks health condition labels or unapproved tracking scripts.
* Content and claim guardrails: In healthcare and regulated verticals, AI-assisted copywriting or chat tools must operate under strict editorial boundaries that avoid implying specific clinical outcomes, making diagnostic claims, or violating platform advertising rules. Ask how the vendor configures and enforces domain-specific review rules before content reaches the public.
Contractual exit schedules and data portability evidence
Most vendor evaluations focus heavily on onboarding speed and feature demos while treating contract termination as an afterthought. That imbalance creates severe commercial risk in AI procurement. Because AI systems accumulate institutional knowledge over time, including cleaned document libraries, custom prompt engineering, routing logic, evaluation datasets, and operational logs, an undocumented exit path can trap an organization inside an underperforming or increasingly expensive platform.
Before signing any multi-year or core operational agreement, procurement teams should assemble a dedicated exit schedule binder, maintained either as a physical executive sign-off packet or an indexed digital closing file. Organized with clear tabs covering asset ownership, export formats, transition milestones, and deletion verification, this exit schedule turns portability from a vague verbal promise into an enforceable contractual exhibit.
### Preventing silent lock-in across prompts, workflows, and embeddings
Standard SaaS contracts usually state that customers may export their "customer data" upon termination. In AI platforms, that phrase is dangerously ambiguous. A vendor might hand back a raw folder of uploaded PDFs while withholding the structured knowledge taxonomies, refined prompt templates, agent instructions, scoring rubrics, and custom fine-tuned weights that made the system productive.
Require the exit schedule to enumerate every category of portable asset and specify its exact export format:
* Source files and structured knowledge bases: All uploaded documents, cleaned text chunks, metadata tags, and taxonomy hierarchies exported in open, non-proprietary formats such as JSON, Markdown, or CSV.
* Prompt libraries, agent definitions, and workflow logic: Complete text exports of custom system prompts, retrieval rules, escalation conditions, and multi-step workflow blueprints developed during implementation or paid professional services engagements.
* Audit logs and evaluation benchmarks: Historical query logs, human review records, and test datasets needed for internal compliance archives or model migration testing.
* Custom fine-tuned weights or adapters: If your organization funded custom model fine-tuning or LoRA adapters built on proprietary datasets, establish explicit ownership and portable weight-export rights, or confirm in writing that the underlying base model license allows you to run those weights on your own hardware or another cloud provider.
### Transition timelines and verifiable data destruction
Portability fails when the offboarding window is too short to execute a safe migration. Negotiate a defined post-termination transition window long enough for IT and operations teams to stand up a replacement environment while retaining read-only and export access. Lock in transparent hourly or monthly rates for transition assistance up front so the vendor cannot use offboarding fees as pricing pressure during renewal negotiations.
Equally important is verifiable destruction after your migration succeeds. Require the contract to define three offboarding controls:
* Deletion sequence and deadlines: Exact maximum timeframes for purging primary databases, vector search indexes, cached prompts, staging copies, and rolling encrypted backups once the buyer confirms successful export.
* Sub-processor purge obligations: Written confirmation that the primary vendor is responsible for triggering and verifying deletion across every downstream sub-processor listed in its register.
* Signed certificate of destruction: A formal attestation executed by an officer or security lead of the vendor specifying the date of completion, the systems purged, and any legally mandated archive exceptions.
Testing portability during the pilot stage is the simplest way to validate these terms. Ask the vendor to run a mock export of a test workspace and inspect the resulting files directly. If the export arrives as an unindexed zip archive with broken metadata or missing prompt configurations, fix the gap before signing a production contract.
Procurement scoring and pre-signature verification
Bringing marketing leadership, IT security, legal counsel, and finance into one shared evaluation framework prevents a common organizational failure: marketing selects a tool based on demo polish, IT blocks it months later over data-handling gaps, and the business loses a full quarter of execution momentum. A structured pre-signature verification matrix aligns every stakeholder around inspectable pass conditions rather than subjective impressions.
During final vendor selection, the cross-functional committee should assemble each finalist's submitted documentation into a standardized scoring sheet and grade every domain strictly on supplied evidence. Verbal explanations offered during sales calls should be logged as unverified until backed by a written document or live console demonstration.
* Deployment Architecture; Mandatory Artifact to Request: Signed topology diagram and model provenance list; Pass Condition: Clear separation of local, VPC, or external API calls with named models and fallback paths; Automatic Red Flag: Refusal to name underlying models or vague claims of "proprietary private cloud" without diagrams
* Network and Compute Isolation; Mandatory Artifact to Request: Hosting region schedule, egress rules, and encryption key policy; Pass Condition: Explicit tenant isolation, documented geographic boundaries, and clear hardware-vs-data ownership terms; Automatic Red Flag: Shared developer sandboxes using production data or unrestricted outbound telemetry
* Retention and Sub-Processors; Mandatory Artifact to Request: Layer-by-layer retention table and dated sub-processor register; Pass Condition: Defined purge windows across logs, caches, embeddings, and backups; explicit training opt-out; advance notice of new sub-processors; Automatic Red Flag: Carve-outs allowing "de-identified" prompt reuse for shared model training or undisclosed third-party APIs
* Access and Audit Governance; Mandatory Artifact to Request: Live RBAC walkthrough and sample audit-log export; Pass Condition: SSO/MFA support, zero standing vendor-engineer access, immutable query logs, and human approval gates; Automatic Red Flag: Support staff able to browse live customer prompts without logged approval tickets
* Regulated Boundaries; Mandatory Artifact to Request: Scope-specific BAA (if applicable) and ad-platform data boundary map; Pass Condition: Written alignment between contractual safeguards, downstream BAA coverage, and sensitive-vertical tracking limits; Automatic Red Flag: Blanket claims of "automatic HIPAA compliance" or unvetted data sharing with advertising pixels
* Exit and Portability; Mandatory Artifact to Request: Contractual exit schedule and sample workspace export; Pass Condition: Open-format exports covering prompts, workflows, knowledge bases, and logs; fixed transition window; signed destruction certificate; Automatic Red Flag: Proprietary export lock-in, omitted prompt configurations, or undefined backup deletion timelines
### Running a staged, risk-contained pilot
Even after a vendor clears the document review, never connect live patient records, unredacted customer databases, or production CRM pipelines on day one. Structure every evaluation around a two-stage rollout:
* Stage one (synthetic and public data sandbox): Test accuracy, latency, permission controls, audit-log exports, and offboarding file exports using synthetic intake records and public company materials. Measure whether the system actually improves operational speed, decision quality, or conversion accountability before expanding scope.
* Stage two (scoped production governance): Only after legal counter-signs the data-processing terms, BAA (where applicable), and exit schedule, and IT verifies SSO, egress locks, and logging in the production tenant, onboard a single tightly scoped workflow with designated human reviewers.

FAQ
Q: Does hosting an open-source model locally make a marketing workflow HIPAA-compliant?
A: No. Hosting an open-weight model on local hardware gives an organization stronger control over network boundaries and eliminates external model API calls for those local workloads, yet hardware alone does not establish HIPAA compliance. Regulated workflows still require administrative policies, role-based access controls, audit logging, workforce training, physical security, risk assessments, and appropriate Business Associate Agreements wherever protected health information is handled.
Q: What is the difference between a zero-retention API agreement and dedicated private compute?
A: Under a zero-retention commercial API agreement, your data still leaves your network to be processed on the model provider's external cloud infrastructure, governed by a contractual promise not to store inputs or train shared models on them. Under dedicated private compute, such as a single-tenant VPC or owned local inference hardware, the model executes inside an isolated environment controlled specifically for your organization, reducing third-party data transit and expanding control over logging, model versions, and network egress.
Q: If a marketing agency or vendor owns the local AI hardware, who owns client data?
A: Hardware ownership and data ownership are completely separate. Even when an agency or technology partner purchases, hosts, and maintains local inference servers, the client organization should retain sole ownership of all raw inputs, proprietary knowledge bases, derived outputs, and attribution datasets processed on those machines. Confirm this separation explicitly in your master services agreement and exit schedule.
Q: Which documents should procurement teams demand before starting a paid private AI pilot?
A: Before launching a paid pilot, collect six baseline items: a signed system architecture diagram naming all underlying models, a layer-by-layer data retention schedule, a complete sub-processor register, a written training-exclusion clause, a sample audit-log export, and a draft exit schedule confirming open-format portability. Keep pilot inputs restricted to synthetic or non-sensitive data until final production contracts and security validations are complete.
Q: How can buyers verify that a vendor is not silently routing prompts to undisclosed third-party models?
A: Combine contractual commitments with technical inspection. Contractually, require a binding model provenance list and sub-processor register with advance written notice before any model or provider changes. Technically, review outbound network egress rules during staging audits, inspect API audit logs for model-identifier metadata, and verify whether the deployment can operate with external commercial model endpoints blocked at the firewall level.
